# Expose the product through an MCP server

jooling gives hourly teams "a single, dependable understanding of scheduled work." Managers live in chat and assistant surfaces for large parts of their day; the product should meet them there without forking its truth. The MCP server (Model Context Protocol) turns an AI assistant into a scheduling copilot that reads the same source of truth and edits through the same rules as the web and native apps.

The MCP server is part of the API process, not a separate deployment: the Elysia app hosts the Streamable HTTP endpoint at `/mcp` (`apps/server/src/routes/mcp.ts`), with the protocol tooling living in `apps/mcp` as an embeddable library (`createJoolingServer` for the tool catalog, `createMcpRequestHandler` for the transport with injectable authentication). The library also ships a stdio entrypoint so local clients can talk to a development API. The MCP layer holds no business logic of its own: every tool call executes against jooling's `/v1/integration/*` endpoints over an in-process loopback, so conflict detection, notice windows, unavailability overrides, scope enforcement, and atomic publication stay in exactly one implementation.

Authentication is OAuth 2.1, per the MCP authorization standard, with the authorization server built on `@better-auth/mcp` (the OAuth 2.1 provider configured for MCP, backed by the `jwt()` plugin's signing keys). Access tokens are audience-bound to the canonical resource (`MCP_RESOURCE_URL`, default `<BETTER_AUTH_URL>/mcp`); `requireMcpAuth` verifies signature, issuer, audience, expiry, and DPoP binding, and unauthenticated calls receive the RFC 9728 `WWW-Authenticate` challenge that drives MCP clients through discovery, dynamic client registration (public clients, PKCE), the web app's sign-in (`/oauth`) and consent (`/consent`) pages, and the token exchange. Tokens carry jooling's integration scopes, the same vocabulary as Workplace API keys. Workplace API keys (`jl_live_…`) remain valid directly on `/mcp` and the integration endpoints for CLI and server-to-machine use.

Authorization is resolved once per request by `apps/server/src/integration-auth.ts`: API keys carry their scopes literally and are workplace-bound; human principals — OAuth tokens or better-auth sessions — get scopes derived from their Employment privileges (`schedule.read` ↔ `schedule.view`, `schedule.write` ↔ `schedule.manage`, `workers.read`/`requests.read` ↔ `schedule.view`, `reports.read` ↔ `reports.view`, `requests.write` ↔ `approvals.review`), their workplace resolved from active membership (`x-workplace-id` disambiguates multi-workplace members), manager-shaped access only (worker Employments never act through this surface), and per-employment location scoping applied to reads. The MCP protocol session is stateful but authentication is stateless: every request re-presents its credential, a session only ever answers to the principal that opened it, and a rotated or different credential is rejected with 403.

Publication is the one act with an actor. Principals publish as themselves; API keys act as the Manager who created them, and publishing additionally requires the `schedule.publish` capability. Workers therefore receive exactly the notifications an in-app publish would send, with an honest audit trail. The v1 tool surface is deliberately manager-shaped — published schedules, drafts with conflicts, rosters, worker overviews and availability, open shifts, time-off listings, labor summaries, draft-shift writes, and publish. Worker-self-service actions (clocking, swaps, acceptances) stay out of v1 because Workplace-scoped credentials cannot represent one Worker's consent, and guessing at consent is precisely what the product's language separates (Acknowledgement vs Shift Acceptance). A worker persona, if wanted later, arrives as per-Employment tokens, not broader keys.

The OAuth provider adds its tables (`jwks`, `oauth_client`, `oauth_resource`, `oauth_client_resource`, `oauth_access_token`, `oauth_refresh_token`, `oauth_consent`, `oauth_client_assertion`) via migration 0035. The sign-in/consent pages live in the web app, which is the product's existing identity surface; no separate account system exists for assistants.
